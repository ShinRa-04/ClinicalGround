## Durable storage and canonical ownership

Current source/documentation describes a gateway-centered canonical-session authority: CLI, TUI, Desktop, API, ACP, cron and managed workers can be clients of the profile's owner. Managed worker transcript writes go through runtime-store RPC rather than independently opening canonical storage. This is a scoped architecture statement, not proof that batch runners or every legacy/direct `AIAgent` use follows that same path. [H060: storage guide](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/website/docs/developer-guide/session-storage.md#L5-L15).

The inspected schema separates messages and per-model usage from runtime epochs, session admissions, worker executions and worker receipts. `session_admissions` provides durable sequencing beyond an in-memory chat buffer. Some foreign keys restrict deleting sessions while ledger rows still refer to them. The guide describes SQLite WAL and derived FTS indexes; full portability, migration and repair branches were not executed here. [H033: schema](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_state_common.py#L477-L586), [storage overview](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/website/docs/developer-guide/session-storage.md#L132-L183).

After owner replacement, started admissions and live prior-epoch workers become `unknown`; they are not blindly replayed. New claims refuse while an unknown execution blocks the session. An unknown state acknowledges that an external effect may have happened even though no definitive receipt returned. [H034–H035: recovery](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_state_runtime.py#L390-L404), [claim gate](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_state_runtime.py#L193-L223).

This is a general lesson for any consequential agent: distinguish queued input, started execution, terminal result and uncertainty after owner loss. A prompt saying “continue” does not establish whether it is safe to repeat a previously started action. Automated reconciliation can inspect external operation IDs/readbacks; otherwise an operator may need to resolve uncertainty.

Managed compaction uses a supplied connection to archive/publish the prepared transcript, increment session generation and return its result projection. The enclosing mutation stores the exact-retry receipt on that same transaction connection. Active and archived generations can legitimately contain identical retained text. “Deduplicate identical rows” is unsafe if it destroys lineage or evidence. [H036: compaction](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_state_mutation_compress.py#L1-L27), [enclosing transaction](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_state_runtime.py#L430-L490).

## Profiles are explicit context, not process-global guesses

`get_hermes_home` gives precedence to a context-local override, then `HERMES_HOME`, then the platform default. Windows defaults use a platform-specific root; hard-coding Unix `~/.hermes` is not the general resolver. Named profiles have separate state/configuration directories. Background threads and child processes must retain the owning profile context; otherwise a long-lived process serving multiple profiles can write under the launch profile. [H037: resolver](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_constants.py#L161-L176), [platform default](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_constants.py#L45-L64).

`spawn_context_thread`/`ctx_bound` are examples of propagation helpers; the memory worker similarly binds owner-home context. A clean constructor is insufficient if teardown, delayed callbacks, cache keys, eviction or process-spawn code consult global environment later. Profile separation is operational state isolation; it is **not** by itself tenant-safe OS containment or a verified healthcare access-control model.

## Child agents: scoped workers, not necessarily persistent people

`delegate_task` builds a new agent from a goal, supplied context, derived depth role and filtered toolsets. Child construction sets `skip_context_files=True`, `skip_memory=True`, `clarify_callback=None`, and `iteration_budget=None` to receive a fresh budget. Context isolation is deliberate: the child does not automatically know the whole parent conversation. An explicitly requested memory toolset remains a documented initialization exception. [H038: child construction](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/tools/delegate_tool.py#L229-L313).

Defaults at this pin include 250 iterations per child,24,000 summary-character ceiling, no idle timeout,10 concurrent children, inherited MCP toolsets and max spawn depth 1. The role argument is not a free grant of deeper delegation: capability is derived from configuration and depth. A dynamic parent-headroom budget also bounds returned summaries. [H039: defaults](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_cli/config_defaults.py#L1355-L1382).

The lifecycle API documents capability handles, cooperative cancellation, bounded immutable terminal results/hash and `RECONNECT_UNAVAILABLE` after restart for its in-process retained handles. Durable worker/session ledgers elsewhere do not imply every Python-thread child magically survives a process exit. [H041: lifecycle contract](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/website/docs/developer-guide/subagent-lifecycle-api.md#L27-L68).

A specialist worker, a long-lived role agent and one owner switching role modes are different designs. Hermes supplies mechanisms for child work; it does not prove that one persistent sub-agent per healthcare role is useful or necessary. When merging jobs, compare retained state, tool authority, coordination cost, privacy boundaries, review independence and evidence requirements. Real-world credential/hierarchy analogies should not silently create runtime approvals or tool permissions absent from the environment's contract.

## Tool registration and capability surfaces

The upstream tool guide describes import-time registration and discovery, toolsets that decide exposure, availability checks and agent-level inline interceptors. It recommends capability at the edges: CLI/skills, service-gated tools, plugins or MCP rather than continuously growing a core tool schema. These are documented extension rules, not an exhaustive plugin runtime audit. [Tool guide](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/tools/AGENTS.md#L7-L73).

Plugin kinds have different precedence. General plugins are later-wins; memory-provider discovery is bundled-first; model-provider overrides are last-writer-wins; context engines have a separate ABC and selection seam. Assuming one discovery policy for all extension types can cause shadowing, unwanted activation or duplicate initialization. [H051: documented discovery table](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/plugins/AGENTS.md#L70-L77).

For a new harness, make tool authorization a host-owned decision. Tool schemas should state inputs, outputs, side effects, preconditions, retry/idempotency behavior and failure types. Filter the actual dispatcher as well as the model's advertised schema. A model-selected role or a tool name omitted from a prompt is not a sufficient security boundary.

## Approvals and sandboxing solve different problems

Default approval configuration is `smart`, with cron, single-query and unattended modes defaulting to deny. The approval module keeps per-session state and a default three-consecutive-smart-denial breaker. These checks aim to prevent cooperative mistakes and repeated blocked attempts. [H049–H050: defaults](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_cli/config_defaults.py#L1657-L1686), [breaker/state](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/tools/approval.py#L40-L119).

Hermes's published trust model explicitly distinguishes terminal-backend isolation from whole-process isolation. A container/remote backend may constrain shell and file-tool operations without constraining in-process plugins, MCP or other child execution paths. The policy treats OS containment as the load-bearing boundary; regex scanning, redaction, approval and tool allowlists are heuristics. This is a published model, not an independently executed security audit. [H048: security policy](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/SECURITY.md#L59-L116).

For our eventual construction, select the threat model first: trusted single-user tool mistakes, untrusted retrieved content, malicious plugin, remote messaging actor or multi-tenant isolation. Each requires a different boundary. Do not infer “Docker is required” from this research: the current research uses no runtime sandbox, and a future harness can use a benchmark-provided boundary or another appropriate deployment design.

## Scheduling and gateways are product capabilities

The cron guide describes a per-home tick lock, occurrence accounting, catch-up policy, execution ledger and scoped profile ownership. In the actual scheduler construction inspected here, scheduled agents use `skip_memory=False`, `load_soul_identity=True`, and `skip_background_review=True`; project instructions load only with a configured workdir. This differs from a stale agent guide sentence that says cron skips memory entirely. [H047: actual scheduler call](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/cron/scheduler.py#L2515-L2530), [scheduled ownership rules](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/cron/AGENTS.md#L18-L60).

Gateway adapters add authentication, routing identity, per-session input queues, delivery receipts, streaming protocol reconciliation and process lifecycle. They are more than “call an LLM when a message arrives.” Full platform-specific behavior was outside this workstream. A benchmark harness usually does not need to rebuild a personal messaging product to gain robust task orchestration.

## Observability: distinguish content and operational health

Gateway monitoring defaults disabled, including OTLP export. Its typed events are intended for content-free/redacted operational health and diagnostics. This does not say all local logs, trajectory captures, usage audits or plugins have the same content policy. [H053: monitoring defaults](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/hermes_cli/config_defaults.py#L2074-L2098), [event shapes](https://github.com/NousResearch/hermes-agent/blob/e6f57427c198cfd96854522b7a9159eb007e13c2/agent/monitoring/events.py#L1-L94).

A useful harness event record links run/session/turn/request/tool/worker IDs with active model, context tokens, cache buckets, retries, compression trigger/outcome, duration and effect status. Content logging should be an explicit separate choice, with retention and redaction rules. A log line that says a tool finished is not sufficient evidence of successful external state; retain the structured receipt/readback that justifies the claim.
