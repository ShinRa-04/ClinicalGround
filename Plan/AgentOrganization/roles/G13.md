# G13 — EHR / clinical informatics / application-support professional

[Role analysis index](../ROLE_ANALYSIS.md) · [Audited healthcare dossier](../../HealthcareRoles/roles/G13.md)

**Status:** proposed design inference; actual task assignment and runtime benefit are unverified. The task/tool contract can assign a simulated function even where the analogous human job needs credentials; do not invent extra real-person steps.

## What function are we trying to preserve?

Support reliable health-information systems and authorized workflows.

The linked healthcare dossier contains the responsibilities, scoped decisions and evidence. This analysis does not upgrade its conditions or model contacts into universal facts.

## Specific question

Does a technical operation alter presentation, access or substantive clinical state?

## Provisional conclusion and reason

Prefer explicit access/configuration/tool machinery; role text alone is not enforcement.

An EHR support interface is infrastructure, not a hidden source of decision power.

Primary grouping: [W22 — Privacy and system-access controls](../WORK_PACKAGES.md#w22). Constrain record access, authorized operations and technical identity/support.

## Can its work be merged?

Prefer explicit permission/configuration machinery plus escalation where uncertain; a persona alone cannot enforce access.

**Boundary that must survive:** Technical access is not consent, clinical permission or substantive authorship; privacy purpose and special restrictions remain explicit.

A common work package is not proof that one employee may perform every activity, or that one persistent LLM is best. A shared adapter, a role mode and a separate worker are all alternatives.

## Information and output contract

Context from the prior proposed model: Approved requirements; Incident and data-quality reports.

Potential work products from that model: System change/support resolution; Audit and validation information.

For a software invocation, add case/stage, source versions, explicit unknowns, allowed operations, requested output, current owner and stop condition. These are proposed internal fields, not verified API parameters or mandatory institutional forms.

## Counterexample and reconsideration

**Failure to detect:** System access is used to rewrite a clinical fact without an authorized author.

**Reason to split/revise the package:** Every worker receives all tools/data because one shared model is assumed to have global authority.

Test a mode-based owner and a bounded specialist/persistent-worker alternative against the same task-visible facts and declared resource constraint; preserve source, authority and completion distinctions. No such comparison has run.

## Remaining uncertainty and evidence

Technical configuration permission is not permission to alter clinical facts or approve care.

**Prior applicability:** Clinical informaticists may hold additional licenses; distinguish technical permissions from those independent credentials.
